# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Kickoff Draft**: a head-to-head fantasy draft league for the Premier League, the format American fantasy players know from the NFL (snake draft, waivers, weekly head-to-head), which the official Fantasy Premier League game does not offer well. Alongside the draft league, a Svelte/Vite football tracker (FotMob-style live scores, league table, fixtures, player stats) covers the Premier League and the Champions League with a competition switcher, with the other European cups on the roadmap. Hosted as a static build on GitHub Pages at the custom domain `kickoffdraft.com`. `src/App.svelte` owns the application shell while the existing plain-JavaScript feature modules remain framework-independent.

Renamed from **Squad Goals** (see git log for when). The rename is user-facing copy only: the Cloudflare Worker service (`goon-squad-data`), the D1 database (`squad-goals`), the GitHub repo, every KV namespace and Durable Object binding, and internal code comments all deliberately keep their original names, since renaming infrastructure identifiers risks breaking a live deployment for no user-visible benefit. `docs/design/squad-goals.dc.html`, the design export this UI still implements, also keeps its old filename; do not churn it.

The UI implements the "Squad Goals" design (source of record: `docs/design/squad-goals.dc.html`, exported from the Claude Design project, kept under its original name per the paragraph above): navy `#0A0E14` background, lime `#C8F542` accent, Archivo with italic-uppercase display type, card surfaces `#12181F`. Sections are Scores, Fantasy (the H2H draft league) and Paper Run (Play). Design tokens live at the top of `src/styles.css` and keep the pre-reskin custom-property names so carried-over components restyle automatically.

The app began as a World Cup 2026 sweepstake hub; the sweepstake (entrants, pot, prizes, Monte Carlo projection) was removed after the tournament. See `README.md` for hosting/deploy steps.

## Commands

- `npm run fetch:live` runs `scripts/fetch-live-data.mjs`: the Go client in `cmd/api-football` pulls API-Football, then the shared JavaScript mapper writes `data/<comp>/live.json`, per-match detail under `data/<comp>/matches/`, and `data/<comp>/scorers.json`. It needs `API_FOOTBALL_KEY`; `API_FOOTBALL_COMPETITIONS` is a comma list of `CODE:season` pairs (default `PL:2026`).
- `npm run fetch:fantasy-players` bakes `data/PL/players.json` from `/players/squads`, with accumulated lineups as an explicit incomplete fallback. The Actions cache and a 24-hour freshness guard prevent five-minute squad refetches.
- Worker (in `worker/`): `npx wrangler login`, `npx wrangler secret put API_FOOTBALL_KEY`, `npx wrangler deploy`. Needs Wrangler 4.36.0+ for the `unsafe.bindings` rate-limit syntax. The fantasy draft room needs the `DRAFT_ROOM` Durable Object binding (`[[durable_objects.bindings]]` plus a `new_sqlite_classes` migration in `wrangler.toml`), deployed the same way, no separate setup step.
- Tests: `npm test` and `go test ./...`. Preview/build: `npm run dev` and `npm run build`. `npm run build` also pre-renders the `/learn/` tutorial pages and regenerates `sitemap.xml` (see the SEO section); there is no separate command, so a deploy cannot ship a stale sitemap.

## Data flow

`index.html` loads `src/main.js`, which mounts `src/App.svelte`; the shell then starts `src/app.js`. `loadModel()` (`src/data.js`) turns raw feed data into the single `model` object every view reads. Existing feature renderers still return HTML strings and use delegated event listeners inside the Svelte-owned shell.

Two delivery paths for the same raw shape (`{ source, lastUpdated, competition, season, matches, standings }`):

1. Cloudflare Worker (`worker/worker.js`) proxies API-Football with the key kept server-side and edge-caches each upstream call, so many pollers collapse into roughly one upstream call per window. The site polls it live.
2. GitHub Action (`.github/workflows/pages.yml`, hourly from 11:00 to 22:00 UTC) bakes `data/live.json` into each deploy as the static fallback.

`src/data.js` picks the source: `loadModel(comp)` tries the `DATA_API` Worker origin first (`/:comp/live`) and falls back to static `data/<comp>/live.json` if the Worker is unreachable. Match-scoped routes carry no competition segment because API-Football fixture ids are globally unique; the Worker validates ids against configured competitions.

Live updates without a deploy: `app.js` re-runs `loadModel()` on a timer (20s while a match is live, 60s otherwise) and only re-renders when a match signature (id/status/score/minute) actually changes.

Upstream polling is a state machine, not the browser cadence. The season schedule is cached for six hours. Fixtures more than two hours away make no status call; upcoming fixtures are batched on a 15-minute cache clipped to expire at kickoff; kickoff-wait and live fixtures are batched separately on a one-minute cache; a known final state is removed from polling. Staggered pre-match fixtures must never inherit a live match's one-minute cadence. The Pages fallback runs hourly during its 12-hour UTC window.

## Architecture invariants (read before editing mapping, standings, or teams)

- **The canonical team name is produced by `normalizeTeamName` (`src/domain.js`).** API-Football uses full club names, so `TEAM_ALIASES` maps provider spellings to the established app join keys used by standings, events, badges, fantasy and the Golden Boot.

- **Team badges prefer a self-hosted crest, then the feed's crest, then a TLA ring.** `LOCAL_CRESTS` is a narrow style override for the current Premier League clubs. Promotions and other competitions must continue to flow from API-Football rather than growing the hardcoded map.

- **Table zones are per-competition config, not hardcoded positions.** Adding a competition means adding its API-Football league id and zones in `src/competitions.js`, then including it in `API_FOOTBALL_COMPETITIONS`; renderers do not change.

- **`mapApiFootballMatches` and `mapApiFootballMatchDetail` (`src/mapApiFootball.js`) are the ingestion contract.** The Worker, build-time bake, and browser consume the same mapped shape. Keep status, round, team-name, card and penalty translation centralized there; the Go command deliberately transports raw payloads without duplicating mapping logic.

- **AI match analysis is cron-generated in the Worker, never on user visits.** A one-minute cron trigger (`[triggers]` in wrangler.toml, `scheduled` handler in worker/worker.js) checks the feed and writes one Claude analysis per live match, plus a full-time read within 48 hours of the whistle, into the `ANALYSIS_CACHE` KV under `analysis:latest:<id>`. `analysisCacheSignature` plus `analysisEventSignature` (red cards, from match detail) decide which ticks regenerate: goal, red card, penalty and status changes immediately, otherwise 10-minute clock buckets in normal play, 5-minute buckets in extra time, and penalty-score changes during a shootout. `GET /analysis/:id` is a pure KV read; the prompt is built server-side via the pure shared module `src/analysisPrompt.js` (league table context, zones, form), so browsers can never trigger an Anthropic call. The schema fields are `{ headline, match, context }`; bump `ANALYSIS_PROMPT_VERSION` when the prompt or shape changes meaningfully. Requires the `ANTHROPIC_API_KEY` secret and the `ANALYSIS_CACHE` KV binding; missing either means no analyses and `matchDetail.js` hides the card. Model comes from the `ANTHROPIC_MODEL` var (default `claude-sonnet-5`; overrides must support adaptive thinking and structured outputs). The Worker depends on `@anthropic-ai/sdk` and `@pushforge/builder` (the repo's only npm dependencies, both Worker-side) and `wrangler.toml` needs `compatibility_flags = ["nodejs_compat"]`. `wrangler.toml` pins `account_id`: the wrangler login sees two accounts and unpinned commands can silently target the wrong one.

- **Accounts are D1-backed opaque bearer sessions; Google is only the identity check.** `POST /auth/google` verifies a Google Identity Services ID token via Google's tokeninfo endpoint, then checks `aud`/`iss`/`email_verified` itself, upserts `users`, and returns a random session token whose SHA-256 (never the token) is stored in `sessions` (30-day TTL). The client keeps the token in localStorage (`gs-session`) and sends `Authorization: Bearer`; there are no cookies, so the cross-origin Pages↔Worker split just works. `GET /me`, `POST /follows/toggle` (competition+team, capped), `POST /prefs` (notification prefs stored now, delivered in Phase 3), `POST /auth/logout`. Missing `DB` binding or `GOOGLE_CLIENT_ID` → 501 and the You section explains itself instead of erroring. The Google client id is public config, set in TWO places: `GOOGLE_CLIENT_ID` in `wrangler.toml` and the constant in `src/account.js`; both empty ships the UI with sign-in dormant. Schema lives in `worker/schema.sql` (idempotent; applied with `wrangler d1 execute`).

- **Push notifications are cron-diffed server state, never client polling.** The minute cron (`runScheduledNotifications`) diffs each live/recent match against `notify_state` in D1 and fans out VAPID Web Push (encrypted by `@pushforge/builder`) for kickoff, goals, red cards (from the same match detail the analysis pass fetches, riding the edge cache) and full-time, plus "analysis ready" only for the full-time read. Targeting is `follows` × `push_subscriptions`, filtered per user by `users.prefs` with `DEFAULT_PREFS` fallbacks; a first sighting of a match only baselines `notify_state` so a deploy mid-match never bursts catch-up pushes; 404/410 from a push service prunes the subscription. The VAPID public key is set in TWO places (`VAPID_PUBLIC_KEY` in wrangler.toml and the constant in `src/push.js`); the private half is the `VAPID_PRIVATE_JWK` secret. `sw.js` at the repo root shows the payloads; `POST /push/test` sends to the caller's devices so delivery is verifiable without waiting for a goal. Device state (`pushState` in `src/push.js`) is always read from the browser's real permission + subscription, never a stored flag.

- **Scorer data is aggregated at build time.** `scripts/fetch-live-data.mjs` tallies cached match-detail files through `aggregateScorers` into `data/<comp>/scorers.json`. Changing a season means clearing the detail directory and changing the Action cache key (`api-football-data-2026-`).

- **Everything the bake writes must be in the Action cache path, because a push deliberately skips the fetch.** `data/*/live.json`, `data/*/scorers.json`, `data/*/matches` and `data/PL/players.json` are all restored from the `api-football-data-2026-` cache. Anything the fetch produces that is NOT listed there silently falls back to whatever is committed in the repo, and the committed copies are football-data.org era seeds whose fixture ids do not match the API-Football ids the Worker serves: a browser on the static fallback would then ask the Worker about matches it has never heard of. This is invisible in CI, because the deploy succeeds either way. Verify a data change by reading the file back off the deployed site, never by reading the workflow's status.

- **The fantasy draft room's Durable Object is a pure cache of the append-only D1 pick log, never the source of truth.** `FantasyDraftRoom` (`worker/draftRoom.js`, one instance per league via `idFromName(String(leagueId))`) rebuilds its in-memory snake-draft state from `fantasy_draft_picks` on every wake, so a DO eviction mid-draft loses nothing; every pick is written to D1 (`fantasy_draft_picks` plus `fantasy_rosters`) before it is ever broadcast. Snake order, pick validation (already-drafted, position-bucket-full) and the deterministic autopick all live in the pure, unit-tested `src/draftLogic.js`, mirroring `src/fantasyScoring.js`; the DO only wires those functions to WebSockets and the pick clock. Auth happens entirely at the Worker edge (`handleFantasyDraftWs` verifies the bearer session and league membership against D1 before forwarding the upgrade), never inside the DO, which trusts only the `X-Draft-User-Id` header on the forwarded request. Sockets use the WebSocket Hibernation API (`state.acceptWebSocket`, `serializeAttachment`) so an idle draft burns no duration, and the 60-second pick clock is a DO alarm, not a timer that would die with the instance. Requires the `DRAFT_ROOM` Durable Object binding in `wrangler.toml`; missing it is a 501 on the fantasy routes, same as a missing `DB`.

- **An odd-sized league plays "Average" instead of taking a bye, and Average is DERIVED at read time, never stored.** A round-robin over an odd number of managers leaves one unpaired every gameweek (`roundRobinSchedule`, `src/draftLogic.js`, pads with a null and drops that pairing); that manager used to score nothing, so a 9-manager league forfeited four weeks per manager per season. `src/fantasyAverage.js` instead pairs them with a virtual opponent scoring the **MEDIAN** of the managers who actually played each other. Median rather than mean despite the name, because a fantasy gameweek has fat tails and a mean opponent turns "did you have a good week" into "did anyone else have a great one"; this is also the established shape of the feature (Sleeper and NFL.com both ship it as the league median). **The unpaired manager's own score is excluded from the median they face**, or scoring more would raise the bar they must clear. There is no `users` row, no `fantasy_league_members` seat and no stored fixture: `AVERAGE_USER_ID` is the sentinel `0` (real ids are AUTOINCREMENT and so always >= 1), and `withAverageOpponent` synthesises the fixtures and the pseudo-member for `standingsFromFixtures`, exactly as `resolveEffectiveLineup` resolves rather than copy-writes. A persisted phantom would need a real user id to satisfy `fantasy_h2h_fixtures`' foreign keys and would then have to be hand-excluded from the draft, rosters, lineups, waivers, autopilot, push and recaps, every one of which correctly ignores it today by never seeing it. A gameweek still being scored yields NO Average fixture rather than a result against a zero that has not finished counting, and more than one unpaired manager (a partial fixture set, not a round-robin) yields none either rather than guessing. Average is chipped `AVG`, deliberately never the `BOT` chip: a bot is a real seat with a real squad a person could have taken, and calling Average a bot would claim a manager exists where none does. Bot managers remain available as a separate, opt-in way to fill a room.

- **The autopick takes the BEST player left on the manager's own board, never the scarcest position, and it ranks the pool itself rather than trusting the caller's array order.** `autoPick` (`src/draftLogic.js`) runs `rankDraftPool` (`src/fantasyDraftRank.js`, value over replacement) over whatever it is handed and returns the highest-ranked player whose position bucket is not already full, so the clock-expiry pick, every bot pick and the suggested-pick card all agree with the board the manager is looking at. It previously filled the scarcest unfilled bucket first, and GK has the fewest slots (2), so **every manager's first two picks were goalkeepers**: an all-bot 8-manager draft opened with 16 straight keepers and left Haaland on the board until pick 18, while the suggestion card advised humans to open with a keeper too. Compounding it, "highest-listed player" meant the raw `data/PL/players.json` array order, which is grouped by CLUB and sorted only by tier (`sortPlayerPool`, `src/fantasyPlayerTier.js`), so the rest of an autopicked squad came out as most of whichever club is listed first. Ranking inside `autoPick` is the fix for that second half: three separate call sites (the Durable Object alarm, the demo, and the suggested-pick card) each passed the unranked pool and none of them could be relied on to sort first. Scarcity needs no special handling because `SQUAD_SLOTS` sums to exactly `SQUAD_SIZE`, so a manager's unfilled slots always equal their remaining picks and any pick into a non-full bucket keeps a legal squad reachable; thin buckets fill themselves late by becoming the only legal ones left. `leagueSize` reaches only replacement level, so passing it wrong mis-ranks a suggestion but can never make a pick illegal.

- **A fantasy gameweek is a WINDOW of wall-clock time, and a fixture belongs to whichever window contains its actual kickoff. It is never the provider's `matchday` label.** `src/fantasyCalendar.js` derives 38 windows from the season schedule itself: each matchday's anchor is the MEDIAN kickoff of its fixtures, and the boundary between two gameweeks is the midpoint between their anchors. The median matters because the calendar is rebuilt from the live feed, which already carries a rescheduled kickoff, so a min/max anchor would let one postponed fixture drag its own window across half the season; a minority of moved fixtures cannot move a median. Verified against the shipped 380-fixture schedule: all 380 map back to their own matchday, so the calendar reproduces the provider's grouping exactly on an undisrupted season and differs only where a kickoff genuinely moved. Boundaries must come from the data, never a fixed weekly cadence (the real season has 20-day international breaks, midweek rounds and a winter break) and never hardcoded dates. `currentGameweekFromMatches(matches, now)` is `max(earliest window still holding an unsettled fixture, the window containing now)`; the second term is a floor and is why the current gameweek **can never move backwards**. Without it, `matchday` (which does not move when a fixture is rescheduled) pinned the whole season at the postponed fixture's original round, silently emptying the standings from that week onward. The consequence managers see is DOUBLE gameweeks (a replayed fixture landing in a later window, so a club plays twice and scores twice) and BLANK ones (a club plays zero times and scores zero, which the My Team pitch head says out loud via `squadGameweekShape` rather than showing an XI that looks broken). `currentFantasyMatches` (`worker/worker.js`) stamps the feed with `assignGameweeks` ONCE per call so every consumer, the kickoff lock included, agrees; `worker/worker.js`'s `currentFantasyGameweek` keeps its `FANTASY_GAMEWEEK_OVERRIDE` dev escape hatch.

- **A player's fantasy points are stored per MATCH, never per gameweek, and a gameweek total is always a SUM.** `fantasy_player_match_scores` is keyed on `(match_id, player_id)`. Its predecessor `fantasy_player_scores` was keyed on `(gameweek, player_id)` and written with `INSERT OR REPLACE`, so a player's second match of a double gameweek silently overwrote his first instead of adding to it. `sumPlayerPoints` (`src/fantasyGameweek.js`) is the one place that accumulation happens, so no caller can rebuild the map with `new Map(rows.map(...))` and drop a match on the floor; `rosterGameweekPoints` takes an already-summed map. The xP blend aggregates in SQL instead, because it divides by gameweeks played and so needs `SUM(points)` with `COUNT(DISTINCT gameweek)`, not a row count. `worker/migrations/002-gameweek-windows.sql` drops the old table (verified empty in production; the old rows carry no `match_id` and could not be split apart).

- **Waivers have a settlement buffer, and a claim is never ambiguous about which run it belongs to.** Both instants hang off the gameweek's LAST KICKOFF, taken from the calendar window rather than an assumed weekly schedule (`waiverRunWindow` in `src/fantasyWaivers.js`): claims submitted from `lastKickoff - WAIVER_QUIET_PERIOD_MS` are accepted but explicitly tagged with the NEXT gameweek and the API says `deferred: true`, and the run refuses to execute before `lastKickoff + WAIVER_SETTLE_BUFFER_MS`. That is a guaranteed four-hour gap between the last claim a run can contain and the moment it reads the claim set. These are LIVENESS numbers only. Correctness is three other things: the unique index on `fantasy_waiver_runs(league_id, gameweek)` plus the single atomic batch (already true, and already enough to make double-application impossible); a trailing `UPDATE fantasy_waivers SET gameweek = next WHERE ... status = 'pending'` as the second-to-last statement of that same batch, which rolls a claim that landed between the run's SELECT and its commit onto the next run instead of orphaning it pending forever; and the claim insert being an `INSERT ... SELECT ... WHERE NOT EXISTS (a run for this gameweek)` with a single bump-and-retry, closing the last interleaving where a run commits between the route reading the timetable and its INSERT landing. `fantasy_waiver_locks` is an advisory lease (guarded upsert to take, released inside the committing batch) that stops two overlapping cron ticks duplicating the work; a stale lease can only ever cost extra work, never correctness, which is why its expiry being a wall clock is acceptable.

- **A manager's absence from `fantasy_lineups` for a gameweek means "use the previous gameweek's lineup", resolved at read time and never copy-written.** `resolveEffectiveLineup` (`src/fantasyLineups.js`) walks a manager's rows for exact-gameweek rows first, else the latest gameweek strictly before it, else no lineup was ever set. A manager who has never set one at all falls back to `defaultLineup` (a deterministic formation-fill over their roster, built on `STARTING_LIMITS`/`STARTING_SIZE` from `src/fantasy.js`), computed fresh on every `GET /fantasy/league/:id/lineup` and never written to D1. `POST /fantasy/league/:id/lineup` validates via `validateLineupSelection` and always writes to the server-derived current gameweek (`currentFantasyGameweek` in `worker/worker.js`, the calendar window still in play, see the gameweek-window invariant above), never a client-supplied one, so a manager can never rewrite a gameweek that has already scored. A set-or-inherited lineup can outlive a roster change; `repairLineup` filters out any starter the manager no longer owns and tops up from the current roster (same formation-fill order as `defaultLineup`), so a dropped player can never leave the resolved XI silently short.

- **Free agency and waivers (Phase 4.4) treat every player, per league, as OWNED, ON_WAIVERS or FREE_AGENT, with the same-position-swap as the one invariant enforced everywhere.** `SQUAD_SLOTS` sums to exactly `SQUAD_SIZE`, so every roster bucket is always full: an acquisition is only ever legal alongside a drop from the SAME position bucket, checked by `validateAcquisition` (`src/fantasyWaivers.js`) on both acquisition paths. A `FREE_AGENT` can be added instantly, first come first served (`POST /fantasy/league/:id/freeagents/add`); an `ON_WAIVERS` player needs a queued claim (`POST /fantasy/league/:id/waivers/claim`) resolved at the next run. In both paths the dropped player lands `ON_WAIVERS`, never instantly re-addable, which is what stops a drop-and-re-add cycle from dodging the queue. A run fires per league once the gameweek has advanced AND its settlement buffer has elapsed (a separate cron pass, `runScheduledWaiverRuns`, see the settlement-buffer invariant above): it resolves every pending claim for the gameweek that just settled via `resolveWaiverRun`, then clears the wire of anything that predates the run. Idempotency is a unique index on `fantasy_waiver_runs(league_id, gameweek)`, the same insert-first pattern as the draft's pick log. Three priority modes live on one league setting (`fantasy_waiver_settings.mode`): `faab` (default, `DEFAULT_FAAB_BUDGET` credits, highest blind bid wins, ties break on league waiver priority then the claimant's own claim order), `rolling` (priority order ascending, winners move to the back after each run via `nextRollingPriorities`) and `reverse_standings` (worst record first, recomputed fresh every run, no persisted reordering).

- **A squad locks for a gameweek at ONE league-wide deadline, the gameweek's first kickoff minus two hours (the FPL model), with each club's own kickoff kept underneath it as a backstop.** `SQUAD_LOCK_LEAD_MS`/`squadDeadline`/`squadLockState` (`src/fantasyDeadlines.js`) derive the instant from `firstKickoffInGameweek` (`src/fantasyCalendar.js`), never a hardcoded date, so a rescheduled opening fixture moves it. Before it, lineups, captaincy and instant free-agent adds are all open; after it the squad is frozen for that gameweek and `handleFantasyLineupSet`/`handleFantasyFreeAgentAdd` (`worker/worker.js`) refuse the write outright. This REPLACED the previous per-player rule (each player locking at his own club's kickoff, ESPN's model) as the thing that decides whether a manager may act, because one announced deadline is what managers mean by "the gameweek deadline" and a squad that decays player by player through a Saturday cannot be counted down to. **`playerLockState`/`lockedPlayerIds` (`src/fantasyLocks.js`) are deliberately NOT deleted**: `playerSquadLock`/`lockedSquadPlayerIds` compose them underneath the deadline, so a club that has actually kicked off is locked regardless of what the deadline arithmetic says. That backstop is what covers a window with no derivable kickoff, a fixture brought forward after the fact, and an unreadable feed. The composed rule is strictly stronger than the old one and `test/fantasy-deadlines.test.js` sweeps a whole gameweek asserting it, because weakening it would reopen the retroactive-lineup exploit (`lineupChangedPlayerIds`, start whoever already scored) that the per-player check was added to close. `currentFantasyMatches` fails OPEN (no feed, no lock) exactly as before, rather than freezing every manager's team on a feed blip.

- **The squad deadline and the waiver timetable are two different instants answering two different questions, and they are provably ordered.** The squad deadline (`firstKickoff - 2h`) governs anything that changes THIS gameweek's scoring: lineups, captaincy, instant free-agent adds. The waiver timetable (`quietFrom = lastKickoff - 1h`, `earliestRunAt = lastKickoff + 3h`, `src/fantasyWaivers.js`) governs which RUN a queued claim lands in; a claim is deliberately NOT gated by the squad deadline, for the same reason the kickoff lock never gated it, because it resolves after this gameweek has settled and therefore changes the NEXT gameweek's squad. Since `firstKickoff <= lastKickoff` and the lead (2h) exceeds the quiet period (1h), `squadDeadline < quietFrom < lastKickoff < earliestRunAt` always, by at least an hour, for every gameweek with any fixture; `gameweekTimetable` returns both together so no caller has to know the second one exists, and `test/fantasy-deadlines.test.js` asserts the ordering across all 38 gameweeks of the real schedule rather than trusting the arithmetic. The user-visible consequence is that in the locked window the Waivers panel says "your squad is locked" and "a claim submitted now is resolved by the gameweek N run" at the same time, and both are true.

- **Pre-season is its own first-class UI state, never a degenerate in-season one.** `seasonPhase` (`src/fantasyDeadlines.js`) reports pre-season while the season's first kickoff (`seasonFirstKickoff`, derived from the schedule) is still ahead, and `deadlineBanner`/`matchupTiming` (`src/fantasyScheduleView.js`) turn that into copy that names the season start and says everything is open, with **no countdown, no quiet-period and no "next waiver run" language at all**. The bug this fixes: three weeks from the opener the app described a deadline and a run as though they were imminent, and rendered an unplayed fixture as a 0-0 scoreline. Two overlaps are load-bearing and both are tested: pre-season and locked are BOTH true for the two hours between gameweek 1's deadline and the opening kickoff (locked wins the headline, the season-start fact survives in the detail, and any copy branching on pre-season alone will contradict the rows below it), and the pre-season framing stops suppressing the countdown once the deadline is within 24 hours, since staying silent on opening morning trades one dishonest screen for another.

- **A commissioner can schedule a still-pending league's draft for a future UTC instant; absence of a row in `fantasy_draft_schedule` means "not scheduled", the pre-existing manual-start-only behavior, which keeps working unchanged.** `validateDraftSchedule` (`src/fantasyScheduling.js`) rejects a past date, an unparseable one, or anything more than `MAX_SCHEDULE_DAYS` out; `POST`/`DELETE /fantasy/league/:id/draft/schedule` are commissioner-only and only while `pending`, and both wipe `fantasy_draft_reminders` for that league so a rescheduled (or cleared-then-rescheduled) time never has an old time's already-sent reminders suppress the new one's. The minute cron's `runScheduledDraftReminders` asks the pure `dueDraftReminder` (also in `fantasyScheduling.js`) which of three kinds, `24h`, `1h` or `start`, is due right now for each scheduled `pending` league, checked against the reminder ledger before sending and inserted into it after (the same "check, act, then mark" discipline as the analysis pass's one-time "analysis ready" push, not the waiver run's stricter insert-first transaction, since nothing here touches roster/money state); once the scheduled instant has arrived or passed, the answer is always `start`, never a stale `24h`/`1h`, which is what stops a Worker outage spanning the scheduled time from announcing "tomorrow" after it has already happened. `start` auto-starts the draft through `startFantasyDraft` (`worker/worker.js`), the exact same helper `handleFantasyDraftStart` calls for a manual/early start, so the two paths can never drift apart; auto-start additionally guards on the league still being `pending` (a manual start winning the race is a no-op here) and at least 2 members, notifying the commissioner with a clear reason instead of silently doing nothing when either guard fails. Draft push notifications target league members directly by user id (`sendDraftPush`), unlike match alerts which target the `follows` table, gated on each recipient's own `draft` preference (`PREF_KEYS`/`DEFAULT_PREFS`, defaulting **true** since joining a league is itself an active opt-in, unlike an optional followed-club alert); `publicUser` merges `DEFAULT_PREFS` underneath whatever prefs JSON is actually stored so an account created before the `draft` key existed still reads it as on rather than requiring a backfill.

- **A bot manager is a member whose clock always expires, and it is unauthenticable BY CONSTRUCTION rather than by a check.** Production had three users, two leagues and zero completed drafts, because a draft league needs eight to twelve people and a new product cannot ask six friends to find four strangers; a league that has not drafted by the season opener is lost for a year. So a commissioner can fill unfilled seats before the draft starts (`POST`/`DELETE /fantasy/league/:id/bots`, commissioner-only AND pending-only, the pair of checks that stops "a commissioner can add a bot" becoming "anyone can add a member to any league"; the remove path additionally verifies the target is flagged `is_bot` AND a member of that same league, or it would be an eviction route). Almost no new draft logic was needed: `FantasyDraftRoom`'s `alarm()` already picks `topQueuedPick(...) ?? autoPick(...)`, and `resolveEffectiveLineup` already falls back to `defaultLineup`, so a bot drafts a legal squad and fields a legal XI with nothing written for it anywhere. **The blocker was identity**, and the answer is that a bot's `users.google_sub` is `bot:<leagueId>:<random>`, which is outside Google's own namespace (Google issues decimal digit strings), so a verified token can never produce a colliding sub; `isRealGoogleSub` (`src/fantasyBots.js`) is the second, independent half, rejecting any non-digit sub in `handleGoogleAuth` before the `ON CONFLICT(google_sub)` upsert can match a bot row and mint it a session. `users.is_bot` is a convenience flag for labelling and exclusion, never the authority. The pick clock is now a decision, not a constant (`pickClockMs`): a bot gets `BOT_PICK_CLOCK_MS`, because an eight-bot league at the human 60 seconds is two hours of nothing happening and filling the seats would be pointless. **A bot is labelled everywhere it appears** (lobby, draft order strip, on-clock card, pick feed, standings, matchup, roster board, league feed, invite preview) and no count that implies a real person is ever reported bare: the seat split is `seatSummary`, and a bot's stored display name itself begins with "Bot" precisely because the league feed denormalises names into its payload on write and the weekly recap hands them to a model, neither of which has anywhere to put a chip. Bots stay IN the recap's numbers (their results are real results and dropping them would contradict the standings) but carry `isBot` so the prompt forbids giving one intent. Bots receive no push (`sendLeaguePush` filters them, though they can hold no subscription anyway) and submit no waiver claims (see the comment on `runLeagueWaiverRun` for why that is a scope line, not an oversight). `test/draft-room-bots.test.js` drives the real Durable Object class through a full 120-pick draft with NOBODY connected, which is the case that matters and the one most likely to break.

- **The defending champion is the one league fact the app CANNOT derive, so the commissioner sets it by hand.** Every settled result lives in `fantasy_h2h_fixtures` forever and the final table is derived from exactly those rows, so from the moment a league plays a gameweek here its champions are computable with nothing recorded during the season. What is not computable is a season the app never ran, and a league arriving from a spreadsheet, a group chat or another product brings one with it; issues #43 and #45 were closed as "wait for May" on the assumption that a previous winner had to be earned in-app, which quietly made a new league's history unrepresentable forever. `fantasy_leagues.previous_winner_user_id` (nullable, `ON DELETE SET NULL` so losing an account never takes the league with it) is that seed value, set through `POST`/`DELETE /fantasy/league/:id/champion`. Commissioner-only, and deliberately **NOT pending-only like the bot routes**: filling a seat changes who drafts and so must happen before the draft, while recording who won last season changes nothing about play and is just as true in May. The target must be a member of THAT league (a bare user id with nothing scoping it would store cleanly and then silently never match anybody) and must not be a bot, since a bot seat is created for this league while it is still pending and cannot have won a season that predates it. It is ONE holder rather than a table of past seasons on purpose: the app has no notion of a season anywhere, so a history table would mean inventing a season vocabulary to hold data nobody has entered; when the app has completed a season of its own that champion is a DERIVED fact and belongs in its own table. The Worker sends the holder as a single id on the league and `withChampionFlags` (`src/fantasyChampion.js`) expands it onto member rows once, where the league detail lands, so the standings, matchup and schedule reads need no champion field of their own and cannot disagree. The trophy is chipped everywhere the league sees a manager once (standings, lobby, matchup, draft order, pick feed, roster board, invite preview) but deliberately NOT on the 38-row season schedule: the BOT chip must appear at every single appearance because omitting it misleads, whereas a trophy repeated once per gameweek is wallpaper.

- **A shared invite link shows the league BEFORE asking for a sign-in.** `GET /fantasy/invite/:code` is the only public fantasy route: league name, seat split and manager display names, with no ids, no email addresses and no echo of the code, `Cache-Control: no-store`. It is safe to serve unauthenticated because the invite code is already a bearer capability worth strictly more than the payload (holding it lets you sign in and join, which reveals everything). The client route is `#join/<code>` and it is its own section rather than a state of Fantasy, because it must render with no session. **Signing in from that screen's own GIS button is the consent** (`mountSignIn`'s `onSignedIn` finishes the join); it is deliberately NOT hooked to the generic account-change listener, which also fires on a session restore at boot, so a visitor who was already signed in when the link opened still presses Join. Opening a link is never consent to be added to somebody's league.

- **The league feed is ONE append-only stream carrying both the app's own events and managers' messages.** `fantasy_chat_messages` has a `kind` of `message` (a human wrote it; `text` is the content) or `system` (the app wrote it; `event` names what happened and `payload` is JSON carrying FACTS, never pre-rendered prose). Wording is produced at READ time by `describeChatEvent` (`src/fantasyChat.js`), so a copy change never leaves old rows speaking an older dialect; payload values are denormalised on write (a manager's display name is copied in, not joined) because the feed is a permanent history that must keep reading correctly after a rename or a deleted account. Splitting chat from the transaction log is exactly the design that fails: built-in league chat is abandoned on ESPN and Yahoo and heavily used on Sleeper, and the difference managers name is that the move and the reaction to it are the same timeline. So Feed leads the sub-tab bar, one tap away from everything; `defaultFantasySubTab` (`src/app.js`) lands a `complete` league on My team (the screen a manager opens the app to act on; see its comment for why Feed lost the landing slot), a `pending` league on its lobby (invite code, schedule, start) and a `drafting` one on the board. Which tabs exist at all is `fantasySubTabAvailable` (`src/fantasyView.js`): Matchup, Standings and Waivers only once the draft is `complete`, My board only before then, so no tab ever offers a step ahead of where the league actually is; the tab bar's disabled attributes, app.js's deep-link restore clamp and the body guards all read that one function. Events are emitted where the change already happens, never by polling for diffs: league created/joined and lineup set (`worker/worker.js` routes, and only when `lineupChangedPlayerIds` says something actually moved), draft started (`startFantasyDraft`), each pick and draft completion (`worker/draftRoom.js`, folded into the SAME `env.DB.batch` as the pick so the unique index rolls back a phantom announcement, and carrying `viaQueue`, which D1's pick log has no column for), waiver runs (folded into `runLeagueWaiverRun`'s single atomic batch) and the weekly recap. Both directions of `GET`/`POST /fantasy/league/:id/chat` are membership-checked, unlike publicly-readable match banter, and a reaction's target message is verified to belong to the calling league because message ids are globally sequential. The draft room accepts a `chat` WebSocket message OUTSIDE `blockConcurrencyWhile` (it contends for nothing) and persists to the same table, so the conversation survives the draft ending.

- **Upstream API-Football usage is measured at ONE chokepoint, and a cache hit is never counted as spend.** `fetchJson` (`worker/worker.js`) is the only place any upstream call is made, so it is the only place usage is recorded; anything measured further out would be a second count to keep in step. The subtlety the accounting exists for: those fetches use `cf: { cacheEverything: true }`, and a response served from the edge REPLAYS the stored rate-limit headers, so a cache hit reports a stale `remaining` that is neither spend nor a trustworthy gauge reading. `isUpstreamHit` (`src/apiQuota.js`, pure, its maths deliberately untouched) reads `cf-cache-status` to tell them apart, and `usageRecord` nulls a cached response's quota headers rather than storing them as if they described the present. Recording is an in-memory counter bump keyed on `(day, endpoint, upstream)` (`src/apiQuotaStore.js`), never a row per request: `fetchJson` runs on every proxied poll of a live match and a D1 write there would be a write per poll. The flush is handed to `ctx.waitUntil` at the TOP of a later request, so it can only ever be writing calls that already finished, plus a forced flush as the LAST cron pass (`runScheduledApiUsage`, after the recap: analytics failing is a blank chart, scoring or waivers failing corrupts a season). Recording is wrapped so a measurement fault can never break the request it is measuring, and the buffer is drained rather than copied on flush, because an undercount degrades a chart where a double-count would make the projection cry wolf. **The counts are therefore a floor, not a ledger** (an evicted isolate takes its buffer with it), which is fine for the number that matters: eviction is uncorrelated with cache status, so `cacheHitRate` stays honest even when totals undercount, and the daily projection is anchored on the provider's own `limit - remaining` where available (`reportedUsage`) precisely because the same key is also spent by the hourly Pages bake and the player-pool script, neither of which passes through the Worker. `GET /health/quota` is the read side: unauthenticated and read-only like `/health/draft-ready`, aggregate counts and the provider's allowance only, no user data. Tables are `api_usage_daily` and `api_usage_quota` in `worker/schema.sql`, pruned to 14 days by the same cron pass.

- **Upstream deduplication is a property of the program, not a hope about Cloudflare's edge cache, and the daily allowance is 7,500 calls.** Several call sites used to say they "reuse the same fetch" or "ride the edge cache"; none of them enforced it, and production disagreed. Measured on the real Worker against a stub upstream: ONE pre-season cron tick issued **16** upstream requests, because `getLive` is called eight times a tick (analysis and notifications once per configured competition, then scoring, waivers, the xP blend and recaps once each for PL) and each issues the same season-schedule and standings URLs. With ten live matches a tick issued **82**, since the analysis and notification passes each fetched all three match-detail payloads for every live match. Against a 7,500/day cap that is roughly 30,000 calls on a matchday, four times over, and exhaustion is not a bill: `getLive` is what fantasy scoring, waiver runs, gameweek derivation and the kickoff lock all read, so a spent key stops the season. `fetchJson` therefore memoises every successful payload in-isolate for **exactly the `cf.cacheTtl` the call site already declared** (`src/apiCache.js`), which is what makes it safe by construction: it can never serve anything staler than the code already told Cloudflare it would accept, so the batched live-fixture request keeps its 60-second window and live scores are unaffected. Concurrent callers share one in-flight promise, because two passes reaching the same URL microseconds apart would both miss a memo that is not populated yet. Errors are never memoised (a one-second blip would otherwise be replayed for six hours). A memo hit is counted as neither spend nor a cached call, deliberately: `cacheHitRate` means "the share Cloudflare's edge absorbed", and folding our own memo into it would hide a regression in the cache we do not control. **INVARIANT: an upstream payload is shared by reference, so consumers must treat it as read-only.** After this, a pre-season tick costs 4 on an isolate's first tick and **0** for the next six hours, ten live matches cost **13.87** a tick, and a repeated match-drawer open costs **0**.

- **When the allowance runs low the Worker degrades in a fixed order, and it fails OPEN.** `src/apiBudget.js` maps the provider's own remaining count (never our own counting: the same key is spent by the hourly Pages bake and the player-pool script, neither of which passes through the Worker) onto three levels at fractions of the provider's stated limit, so a plan change moves them without a deploy. The order, cheapest to lose first: AI analysis, then the drawer's lineups and player stats, then the drawer's remaining upstream calls. **Never shed at any level: `getLive` itself and every fantasy cron pass**, because those are the season and a match drawer is not. At the tightest level `GET /match/:id` is built from the fixture summary `findKnownMatch` already returned (`mapApiFootballMatchDetailFromSummary`) for **zero** upstream calls and still shows teams, score, kickoff and venue, reporting what it skipped on the existing `detail.degraded` rather than inventing a second vocabulary for the client to handle. That route is singled out because its cost scales with TRAFFIC while every cron pass is fixed, which is the dangerous shape against a hard cap. Failing open is enforced in two directions: an unreadable gauge is `normal`, never `critical` (note `Number(null)` is `0`, so a missing reading must be rejected before coercion or it reads as "none left"), and a limit of zero or less is treated as unknown rather than pinning the Worker at `critical` forever. The gauge is `latestQuota` in `src/apiQuotaStore.js`, a sticky isolate-lifetime reading that survives `drainUsage` on purpose: `quota` is ledger material and must not be written twice, this is a live gauge, and one that blanked itself on every flush would hand the guard rail "unknown" every thirty seconds.

- **`GET /match/:id` fans out to four upstream payloads, and exactly one of them is load-bearing.** The fixture payload IS the match (teams, kickoff, venue), so it stays strict and a failure there is still a 502. Lineups, events and player stats are supplementary and go through `fetchSupplementaryJson`, which logs the endpoint and serves an empty payload instead of throwing. Before that, any single hiccup on one of the three, an error-shaped payload, a non-2xx, a per-minute rate limit, discarded the fixture payload that had already arrived and 502'd the whole read; a fixture that has not kicked off has nothing for those three to return anyway, so the failure mode was maximally wasteful. Note what was NOT the cause: an *empty* payload (`results: 0`, `response: []`) has always mapped cleanly to a detail with no timeline, which is the correct pre-match answer. A degraded read names which endpoints degraded on `detail.degraded` (a bare flag would not have told anyone which of the four to look at) and is browser-cached for `MATCH_DETAIL_DEGRADED_MAX_AGE` instead of the resting five minutes, so a blip cannot outlive itself in every reader's cache. `src/matchDetail.js` already renders a match with no timeline and no lineups as a pre-match note, so the drawer needed no change.

- **The weekly AI recap states only numbers this server computed; the model writes prose and cannot author a figure.** `src/fantasyRecap.js` derives the power rankings (`buildPowerRankings`, a points-unit blend of recent form, season output and win rate), the movement, the matchup results and the awards (bench king, worst captain call, luckiest win against the league median) from `fantasy_gameweek_scores`, `fantasy_h2h_fixtures`, `fantasy_lineups` and `fantasy_player_scores`. `src/fantasyRecapPrompt.js` hands them over as data, and `RECAP_SCHEMA` has **no numeric field at all**, so the model returns prose keyed to ids and `mergeRecap` joins it back onto our own rows: a note for a manager it invented is dropped, an award it hands out that we reported null never renders. Users of competing products forgive a bland recap and do not forgive a confidently wrong one, which is why the split is structural rather than a prompt instruction. That module also defines NO notion of player value: value over replacement already exists once, in `src/fantasyDraftRank.js`, and a second competing definition would mean two numbers claiming the same meaning. **Every name reaching the prompt is untrusted user input** (league names, manager display names): they appear in exactly ONE labelled block, every other section refers to managers by a stable server-assigned id (`m1`), `sanitizePromptText` flattens control characters and caps length so a newline cannot impersonate a prompt section, and the system prompt states last that names are data to quote and never instructions to follow. There is deliberately no content filter: Yahoo ships this feature at scale and their own mitigation is report-and-regenerate, which is the tell that filtering adversarial free text loses. Generation is `runScheduledLeagueRecaps`, LAST in the cron (it is the only pass that spends money and the only one nothing depends on), one call per league per settled gameweek, gated on `fantasy_league_recaps`' primary key with the ledger row and the feed message committed in one atomic batch so two overlapping ticks cannot both post. Token usage is logged. A failed model call still posts a recap of pure numbers with empty prose.

- **Every draft pick records HOW it was made, and a bot seat is never counted as an absent human.** `fantasy_draft_picks.via` is one of `manual` (a socket message; somebody was at the keyboard), `queue` (the clock expired and that manager's OWN shortlist supplied the pick: prepared, not present), `autopick` (the clock expired with nothing legal queued; nobody chose this player) or `bot`. `PICK_VIA`/`resolvePickVia` (`src/draftLogic.js`) is the single decision point, so the socket path and the alarm path cannot drift into disagreeing. Before this, the two drafts most worth telling apart were byte-for-byte identical in D1: one where everybody showed up, and one where three of four sleepwalked through on the clock. The older `viaQueue` boolean was not enough, because an autopick with an empty queue recorded `false` exactly like a manual pick. **`bot` outranks the queue/autopick split** because a bot's clock always expires by design; folding it into `autopick` would make a bot-filled league read as a league full of absentees and would drag down the one number this exists to produce. A bot cannot hold a queue at all (no session, so no queue write), so nothing is discarded by that precedence. The column is **nullable and deliberately not backfilled**: NULL means "picked before this existed", and a `NOT NULL DEFAULT 'manual'` would have quietly asserted every historical pick was considered. The persisted feed payload stores `via` ONLY (`viaQueue` is derivable, and storing a derived field in permanent history is how two copies of one fact start disagreeing); `describeChatEvent` falls back to `viaQueue` for older rows. The ephemeral WebSocket messages carry both, so every existing browser reader keeps working. It also fixed a live bug: `_hydrate` used to hardcode `viaQueue: false`, so a Durable Object eviction mid-draft silently relabelled every earlier queue autopick as an ordinary pick. `scripts/metrics/13-draft-engagement.sql` is the read side, and `test/draft-room-bots.test.js` proves all four kinds against the real Durable Object.

- **The post-draft recap is the weekly recap's contract applied to the draft, graded against the board managers actually saw.** `src/fantasyDraftRecap.js` computes every figure (grade, best value, biggest reach, positional strengths and holes against `STARTING_LIMITS`, projected finish) and `src/fantasyDraftRecapPrompt.js` imports `sanitizePromptText`/`managerIdMap` from `fantasyRecapPrompt.js` rather than restating the defences: `DRAFT_RECAP_SCHEMA` has **no numeric field at all**, names appear in exactly ONE labelled block, and `mergeDraftRecap` joins the prose back onto our own rows. It defines **no new notion of player value**: grading runs on `rankDraftPool` (`src/fantasyDraftRank.js`), the same board the draft room showed the manager while they were picking, so the app can never tell somebody they reached for a player it had just recommended to them. Two figures are worth knowing. The grade subtracts what the board says those exact draft slots were worth, so **picking first is not an advantage the grade hands you**; and `GRADE_SCALE_FLOOR` floors the curve's scale, because a pure z-score in a two-manager league is always exactly +1 and -1 and would manufacture an A and an F out of a draft decided by a rounding error. Generated once per league by `runScheduledDraftRecaps`, gated on `fantasy_league_draft_recaps`' primary key with the ledger row and the feed message in one atomic batch. The recap lives in its feed payload and nowhere else, so `GET /fantasy/league/:id/draft/recap` (membership-checked) and the feed card can never disagree. "Shareable" is a composed share LINE, not a public route: a league's grades name every manager in it, and `composeDraftShareText` deliberately carries no invite code, since a link that silently joins the sender's private league is not a thing to hand to a group chat.

- **Dead-team autopilot is damage control, and it is off the instant the real manager touches anything.** One abandoned roster hands free wins to whoever plays it and ruins the season for the other nine people, which is why ESPN ships this as Auto Control. A commissioner flags a seat (`fantasy_league_members.autopilot`, `POST`/`DELETE /fantasy/league/:id/autopilot/:userId`); `runScheduledAutopilot` then writes the best legal XI each gameweek and may make ONE conservative same-position pickup. **`AUTOPILOT_ACTIONS` (`src/fantasyBots.js`) is an allowlist, not a list of prohibitions**, precisely so that the day trades ship, an autopilot built on "everything except trades" cannot silently inherit the ability to trade an absent manager's squad away. The seat keeps its real owner throughout: `users.is_bot` is untouched, nobody is evicted, and the league detail payload labels `autopilot` separately from `isBot` because calling an absent person a bot would be wrong. **The reversibility rule is what earns it the right to exist**: `clearAutopilot` runs inside the SAME request that proves the manager is back (lineup, free agent, waiver claim, draft queue or a feed post, the `AUTOPILOT_RETURN_ACTIONS` list), never on the next tick, because a manager who returns to find the app still playing their team would be right to leave. Enabling is commissioner-only; **disabling is also open to the seat's own owner**, so taking your own team back never depends on the commissioner being reachable. The lineup is WRITTEN rather than left to `resolveEffectiveLineup`'s read-time fallback, because that fallback only applies to a manager who never set one at all, whereas an abandoned team is usually the other case: a stale XI inherited forward every week, which is the actual problem. The pickup requires an `AUTOPILOT_PICKUP_MARGIN` edge, respects the kickoff lock exactly as a manager does, uses the same guarded `INSERT ... SELECT` so a real manager racing the same free agent wins, and never queues a waiver claim (that spends FAAB budget an absent manager may want back, which is a decision rather than damage control). Note `bestStartingXi` (`src/fantasyLineups.js`) captains the XI's highest scorer rather than inheriting `defaultLineup`'s "first starter", which `fillLineup`'s GK-first order would have made the goalkeeper: a captain's points are doubled.

- `apiQuotaStore.js` the pure buffering and reporting layer around it: `createUsageBuffer`/`bufferUsage`/`drainUsage` (in-memory counts keyed on day, endpoint and upstream), `usageDay`, `chunkRows` (D1's 100 bound-parameter cap), `reportedUsage` (which "used" figure the projection trusts), `latestQuota` (the sticky gauge the budget guard rail reads, deliberately not cleared by a drain) and `buildQuotaReport` (the whole `/health/quota` payload). Read its header before changing how usage is counted.
- `apiCache.js` the pure TTL policy behind `fetchJson`'s in-isolate response memo: `createResponseCache`, `readCached`/`writeCached` (window clamped to the longest declared `cf.cacheTtl`, nothing stored for a non-positive ttl), `pruneCache`, `cachedEntryCount`, `cacheStats`. Bounded and least-recently-used. Read its header before changing how upstream responses are reused.

Fails open by design; see the invariant above before changing a threshold.

- `analysisPrompt.js` pure AI-analysis prompt builder (system prompt, JSON schema, per-match payload with league context); imported by the Worker only.
- `views.js` HTML-string renderers (ticker marquee, competitions sidebar/chips, hero, scores tab bar, live cards, match lines, league table, mini-table aside, knockout board, fixtures, player stats, footer).
- `format.js` pure formatters and live/finished status helpers (no DOM).
- `interactions.js` `confettiBurst` (currently unwired; kept for celebration moments).
- `matchDetail.js` match drawer: right slide-in with score header, then AI analysis, timeline (goals/cards/subs merged in match order), line-ups and banter in one scroll; fetches per-match detail on open (Worker `/match/:id` or static `data/<comp>/matches/<id>.json`).
- `banter.js` shared per-match reactions and messages, D1-backed. Reading is public; posting requires a signed-in session (names come from the account, no client-supplied identity). POST responses are strongly consistent, so the optimistic UI reconciles against them without flicker; an `inflight` counter drops poll responses that would race a pending post.

Client-side only, never touches a real league.

## Adding a tab or panel control

- **New scores tab:** add it to `SCORES_TABS` in `src/views.js` (label + key) and to `SCORES_TABS` in `src/app.js`, add a `case` to `renderPanel` in `app.js`, and write the renderer in `views.js`. Tabs route via the URL hash; the Knockout tab demonstrates conditional presence (cups only).
- **New in-panel control** (sort toggle, filter): give it a unique `data-*` attribute (not a shared one), keep its state in the `state` object in `app.js`, read it in the renderer, and handle it in `wireLayoutControls` (click delegation with an early `return` per handler). Reuse the `.segrow`/`.seg` pill markup; see `data-fixture-view` (fixtures), `data-gb-sort` (player stats).
- **New tutorial:** add one entry to the `TUTORIALS` array in `src/tutorials.js` with its own `slug` and `sections`, reusing the existing block types; `src/tutorialsView.js`'s index and reader renderers need no change to pick it up, since both just map over whatever is in `TUTORIALS`/a tutorial's `sections`. The next `npm run build` also gives it a public page at `/learn/<title-slug>/`, a sitemap entry, footer and noscript links, and cross-links from the other tutorial pages, with no edit outside `tutorials.js`. Link to it from wherever the confusion actually happens (see the Waivers panel's "How do waivers work?" in `fantasyView.js`, a `data-tutorial-open="<slug>"` control handled by the same click delegation as everything else) with `data-tutorial-open="<slug>"`.

## Telemetry (PostHog)

`src/telemetry.js` initializes `posthog-js` from `VITE_POSTHOG_KEY`/`VITE_POSTHOG_HOST` (EU ingest, `.env.production`; both are public client tokens, the same trust level as `GOOGLE_CLIENT_ID`, safe to commit). `account.js` identifies by email on sign-in and on session restore, and resets on sign-out: email is the identity key because the Worker's `publicUser()` never exposes the internal numeric user id to the client, and email is also the identity the product wants users assigned by. `app.js`'s `metric()`/`log()` helpers translate the old Sentry metrics/logger calls into capture events (PostHog has no separate count/distribution/gauge metric types, so `metric_kind` rides along as a property instead).

- **No module outside `src/telemetry.js` may call `posthog` directly; everything goes through its four wrappers (`track`, `trackException`, `identifyUser`, `resetIdentity`), and none of them can throw.** PostHog is a third-party script talking to a third-party host and is blocked outright for a large share of real users, so a blocked, failed or half-initialised provider has to degrade to "no data" and never to a broken draft room. Wrapping centrally is the point: only `metric()`/`log()` used to be guarded, which left the direct `posthog.capture()` calls in `app.js`, `account.js` and `banter.js` as unguarded third-party calls sitting on user interaction paths. Verified by sabotaging every provider entry point to throw in a live browser and driving the sandbox draft: twelve throws, zero uncaught errors, the app fully functional.

- **The funnel's event names and property builders live in the pure `src/funnelEvents.js`, never inline at the call site.** `FUNNEL_EVENTS` is the whole vocabulary (snake_case, `<surface>_<object>_<verb past tense>`, prefixed `demo_`/`fantasy_`/`user_`); the builders turn live app state into properties and are unit tested in `test/funnel-events.test.js`, because a funnel event with the wrong property is worse than no event, it is a number someone will steer the business by. Two rules hold throughout and are asserted by tests: **no personal data** beyond the existing identify call (a typed team name becomes `named_team: true`, a league's name and invite code never appear at all), and **every builder tolerates null/empty/half-built input** rather than throwing. Properties must make an event answerable rather than merely countable: `demo_abandoned` carries the stage, the overall pick, the league size and the pick clock, since "someone abandoned" is not actionable and "abandoned at pick 9 of an 8-manager draft on a 10-second clock" is. Bot picks in the sandbox are deliberately NOT tracked (they are three quarters of every board and nobody chose them); `demo_pick_made` separates `manual` from `queue_autopick` and `clock_autopick`, which the real draft room cannot do because its autopick happens server-side in the Durable Object alarm and never reaches the browser.

- **`demo_abandoned` is latched behind `exitReported`, and a visitor who never pressed Start is not an abandonment.** `teardownDemo()` runs from `renderLayout` on every paint where the section is not the demo, so without the latch one navigation away would emit one event per subsequent render; `demoAbandonProperties` returns null for the `setup` and `report` stages, which is what stops a bounce already counted by `demo_entered` from also being counted as a drop-out part-way down the funnel.

- **The pre-rendered `/learn/` pages get an anonymous pageview beacon, deliberately not the app bundle.** Those pages load no application JavaScript at all by design (see the SEO section), which left the site's entire organic-search surface completely unmeasured. `renderLearnBeacon` (`src/learnPageView.js`, pure, config threaded from `vite.config.js`'s `loadEnv` through `buildSeoPages`) emits one inline `sendBeacon` carrying `$pageview` with `$process_person_profile: false`, so PostHog records the event and creates no person: person-level tracking would need an identifier persisting across pages, which means a cookie, which means a consent banner on a static article. `distinct_id` is therefore random per pageview and never stored, so **person counts from this source are meaningless and pageview counts are the number**. The URL is origin plus pathname with the query string dropped. Missing config emits no script at all.

Business metrics do NOT come from PostHog. `scripts/metrics/` holds thirteen single-statement, read-only D1 queries (league funnel, draft completion, stalled drafts, time-to-draft, retention, feed and waiver activity, draft engagement) runnable through `wrangler d1 execute --command`, because the owner's PostHog project is not queryable by everyone who needs to steer the business. Read its README before adding one: it records which questions the schema genuinely cannot answer yet (`fantasy_lineups` has no timestamp, and a league has no completion timestamp or target size) and the minimal column that would fix each. The gap that used to head that list, an autopicked pick being indistinguishable from an engaged one, is closed by `fantasy_draft_picks.via`.

When changing the deployed origins, keep `ALLOWED_ORIGINS` (worker CORS) and the GitHub Pages URL aligned. `ALLOWED_ORIGINS` currently lists both `https://henderjm.github.io` and the new `https://kickoffdraft.com`/`https://www.kickoffdraft.com` during the domain move; drop the github.io entry once DNS has propagated and the custom domain is confirmed live, not before.

## Custom domain (kickoffdraft.com)

The site moved from `https://henderjm.github.io/world-cup-sweepstake/` to the apex domain `https://kickoffdraft.com`. A `CNAME` file at the repo root (containing exactly `kickoffdraft.com`) is required by GitHub Pages for a custom domain, and it must be in `vite.config.js`'s `copy-runtime-assets` list like every other static file below, or **Pages silently unsets the custom domain on the next deploy**. `worker/wrangler.toml`'s `SITE_ORIGIN` points at the new domain. The Worker's `DATA_API` origin in `src/data.js` deliberately still points at the `workers.dev` URL, not an `api.kickoffdraft.com` custom domain, because that custom domain does not exist yet; switch it only once it does.

## SEO and social-sharing assets

Head metadata (title, description, canonical, Open Graph, Twitter card, theme-color, the `WebSite` JSON-LD block) lives directly in `index.html`; the `<noscript>` block right after `#app` is genuine crawlable content for clients that do not execute JavaScript, not a pre-mount placeholder, so it must never flash for real users. Share/app-icon images live in `assets/` (`og-image.svg`/`.png` at 1200x630, `favicon.svg`, `favicon-32.png`, `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`); `site.webmanifest`, `robots.txt` and `CNAME` sit at the repo root. All of these are static files, not processed by app code, so **any new one must be added to `vite.config.js`'s `copy-runtime-assets` `closeBundle` list or it will not ship**; verify with a real `npm run build` and inspect `dist/`. Note that Vite's own HTML asset pipeline independently hashes and re-copies whatever `index.html` references by a relative `href` (favicon links, the manifest link), so `dist/` ends up with both the plain copies from the copy list and Vite's hashed duplicates; harmless, but `site.webmanifest`'s icon `src` values are absolute production URLs specifically so the manifest keeps resolving correctly even after Vite relocates its hashed copy into `dist/assets/`.

`robots.txt` now takes effect: it was inert while GitHub Pages served this project at a subpath (`https://henderjm.github.io/world-cup-sweepstake/`, where crawlers instead read the nonexistent `https://henderjm.github.io/robots.txt`), but `kickoffdraft.com` is a domain root, so `robots.txt` and its `Sitemap:` line are now read correctly.

- **The app is one crawlable URL, so the tutorials are pre-rendered as their own static pages at build time, and `sitemap.xml` is generated, never hand-maintained.** The app is hash-routed (`#live`, `#tables`) and client-rendered, so `index.html` is the only URL a crawler sees and hash fragments are not URLs. `src/tutorials.js` is the only content on the site with real organic search demand, so `vite.config.js`'s `seo-learn-pages` plugin emits, on every `npm run build`, `dist/learn/index.html` (the hub) plus `dist/learn/<slug>/index.html` per tutorial, and writes `dist/sitemap.xml` from the same array. **There is no `sitemap.xml` at the repo root and it is deliberately absent from the `copy-runtime-assets` list**, because a checked-in one goes stale the moment a tutorial is added. Adding an entry to `TUTORIALS` is the whole job: it gets a page, a sitemap URL, cross-links from its sibling pages, a footer link and a `<noscript>` link with no other edit. Slug, URL and sitemap logic is the pure `src/learnSeo.js` (the page slug comes from the tutorial's TITLE, `how-waivers-work`, not its terse in-app route slug `waivers`, so retitling a tutorial changes its public URL); the documents are the pure `src/learnPageView.js`; `scripts/build-seo-pages.mjs` is the only piece that touches disk. Prose correctness is inherited rather than forked: content comes from `TUTORIALS` and the blocks are rendered by `tutorialsView.js`'s own exported `SECTION_RENDERERS`, with only the interactive resolver overridden (the static page stacks all three waiver modes instead of hiding two behind a toggle, which is strictly more indexable text and works with JavaScript off). Pages load **no application JavaScript at all**, so nothing may be added that needs the app bundle; they are styled by the app's own hashed stylesheet (the plugin reads its real name out of the bundle in `generateBundle`) plus the "Static Learn pages" block at the end of `src/styles.css`. All asset and internal hrefs are relative (`../../assets/...`) so the pages survive a non-root base, matching `base: "./"`. JSON-LD is `Article` plus `BreadcrumbList` (and `CollectionPage` on the hub), not `HowTo`: these are explainers with no single outcome, and Google dropped HowTo rich results. `lastmod` comes from the commit that last touched the source file, which is why the Pages workflow checks out with `fetch-depth: 0`; a shallow clone falls back to the build date. The same renderers are served from dev middleware, so `/learn/` links are live under `npm run dev` rather than 404ing until someone builds.
